# Privacy data map

This document maps personal data to its storage, purpose and deletion mechanism. Read this when reviewing privacy, adding a data field/export, responding to an erasure request or designing retention. The controller must approve actual school retention periods; repository defaults are not legal policy.

## Inventory

Primary sources are `apps/backend/src/flrc/db/models.py`, `modules/auth/`, `modules/administration/users.py`, `modules/changes/`, `modules/jobs/` and `modules/backup/`. In the school Compose profile PostgreSQL/Redis are school-hosted; a managed profile may use approved remote processors instead.

## Permanent teacher deletion

[ADR-080](../adr/080-a-deactivated-teacher-can-be-deleted-permanently-their-grade.md) is implemented by `DELETE /api/admin/users/{user_id}`. An admin must first deactivate the account; deletion of self, an active user or a demo visitor is rejected. It is **not undoable**.

The operation:

- replaces name with “Silinmiş öğretmen” (deleted teacher), email with a unique `deleted-<id>@deleted.invalid` address, and records `deleted_at`;
- clears Google subject, report name, PNG/digest and privileged role flags;
- deletes assignments and target report-identity audits, deletes unused override grants and expires grants referenced by grade audits;
- scrubs the account's names/email/personal changes/kept images from relevant admin action snapshots, preventing undo from restoring its identity;
- revokes remaining sessions while retaining the user id referenced by grades, grade audits, save batches and jobs.

This is identity erasure within the live database, not deletion of all school assessment history. Backups, downloaded PDFs and existing Drive bundles can still contain the former identity/signature until their separate retention ends. Follow the controller's backup/restore policy so restoring an old dump does not silently reintroduce erased identities. Report renderers hold a teacher's signature only for the render that prints it, never in a process-wide cache, so it is not printed again after the deletion.

## Expiry, hiding and physical purge

- Retiring report columns (“sütun”) does not erase their values/audits. Middle-school English comments are intentionally omitted from normal grids/history/new PDFs under [ADR-063](../adr/063-no-opinion-field-in-middle-school-english.md); authorized audit/workbook exports and backups preserve underlying records. Other programmes retain comments.
- Admin undo is usable for seven days ([ADR-075](../adr/075-admin-changes-can-be-undone-for-seven-days-and-conflicts.md)). Expired action records remain physically stored until purge runs. The nightly scheduler attempts purge before dumping but logs and continues if purge fails; monitor maintenance errors.
- Job download expiry is checked at request time; old blob bytes remain until `flrc purge-job-outputs` or nightly maintenance removes them. Multipart report staging uses a six-hour bound; failed/stale unfinished parts are deleted rather than exposed as completed downloads ([ADR-077](../adr/077-report-sets-larger-than-one-class-are-background-jobs-with-a.md)).
- Direct preview/class PDF responses are not saved as job blobs. Browser downloads, printed copies and Drive archives have independent retention; a server purge cannot revoke them.
- A middle-school English class sheet contains every pupil's number/name and English fields; any authenticated teacher can generate it. Treat it as a whole-class personal-data export, not an individual report card.

Exact maintenance/backup procedures live in [Backups and restore](../operations/backups-and-restore.md) and the [Runbook](../operations/runbook.md). Do not invent one automatic retention period covering grades, audits, jobs, logs, backups and printed records.

## Demo privacy boundary

The demo verifies a Google identity but does not persist the real Google email/name/picture/raw subject. Its keyed subject hash is still a temporary pseudonymous identity link, not anonymous data. The account expires at most 24 hours after creation; session TTL can be shorter. There is no promise of an exact-time background erasure for an idle expired visitor before the next reset/cleanup opportunity.

All demo school records must be synthetic and shared across visitors. Do not import real rosters or signatures. Provider/OAuth access logs are outside the application's database promises; review provider policy independently. See [Public demo operations](../operations/public-demo.md) for reset behavior and [Security model](security-model.md) for access controls.

## Controller checklist

Privately document approved processors/regions, access roles, retention periods per category, backup key custodians, export/printed-copy handling and the erasure/recovery procedure. Test data recovery and erasure using synthetic records. Incident notifications and legal deadlines are the controller/privacy officer's responsibility, not application configuration defaults.
